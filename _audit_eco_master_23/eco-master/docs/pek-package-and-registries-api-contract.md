# API-контракт: комплект ПЭК и предметные реестры

Покрывает эндпоинты, которые использует текущий фронтенд ПЭК: формирование комплекта отчёта и
реестры источников выбросов / выпусков сточных вод / отходов и движения отходов.

Все ответы — стандартный `ApiResponse`:
`{"success": bool, "message": string?, "data": T?, "code": string?, "errors": [string]?}`.

---

## 1. Формирование комплекта

### Признак доступности

`generatePackage` возвращается в **двух** местах и вычисляется **одним** компонентом
(`PekPackagePolicy`), который же и применяется при выполнении операции:

| Где | Когда использовать |
|---|---|
| `GET /api/pek/reports/{id}` → `data.availableActions.generatePackage` | всегда, в том числе когда комплекта ещё нет |
| `GET /api/pek/reports/{id}/package` → `data.availableActions.generatePackage` | когда комплект уже существует |

`GET .../package` отдаёт **404** до первого формирования, поэтому для первой генерации признак
берётся только из `ReportResponse`.

`generatePackage = true` требует одновременно:

1. глобальная роль входит в `PEK_REPORT_EDIT` (`ADMIN`, `DIRECTOR`, `HEAD`, `ECOLOGIST`, `LABORATORY`);
2. в **компании этого отчёта** у пользователя тир не ниже `EDITOR` (`ADMIN`/`DIRECTOR` — сквозной доступ);
3. статус отчёта не `SIGNED` и не `ARCHIVED`.

Ключ `matchSources` не переименовывался и остаётся в `availableActions`. Прочие ключи не менялись.

### POST /api/pek/reports/{id}/package/generate

**`If-Match` обязателен и содержит версию ОТЧЁТА** (`ReportResponse.data.version`).

Не путать три независимых счётчика:

| Поле | Что считает |
|---|---|
| `ReportResponse.version` | оптимистичная блокировка отчёта — **это и есть `If-Match`** |
| `PackageResponse.documentVersion` | порядковый номер комплекта для этого отчёта (1, 2, 3…) |
| `PackageResponse.version` | оптимистичная блокировка строки комплекта |
| `sourceContentRevision` | contentRevision отчёта на момент сборки |

Ответы:

| Ситуация | HTTP | `code` |
|---|---|---|
| успех | 200 | — |
| заголовок `If-Match` отсутствует | 400 | `VERSION_REQUIRED` |
| версия отчёта устарела | 409 | `PEK_VERSION_CONFLICT` (+ `currentVersion`) |
| отчёт `SIGNED` / `ARCHIVED` | 409 | `PEK_REPORT_DOCUMENT_LOCKED` |
| нет тира `EDITOR` в компании / чужая компания | 403 | — |
| в программе нет активных направлений мониторинга | 409 | `PEK_MONITORING_EMPTY` |
| совпали имена файлов внутри комплекта | 409 | `PEK_PACKAGE_DUPLICATE_ENTRY` |

`If-Match: 0` — валидное значение (у только что созданного отчёта версия 0).

Отчёт блокируется `SELECT … FOR UPDATE` до сравнения версии, поэтому две параллельные генерации
сериализуются, а `documentVersion` строго возрастает. Отклонённый запрос не оставляет ни строки
комплекта, ни сохранённого файла.

Подписание закрывает **перевыпуск**, но не доступ: уже собранный комплект остаётся скачиваемым,
`downloadPackage` продолжает отражать актуальность (`sourceContentRevision`).

### `missingFields` — снимок, а не текущая готовность

`PackageResponse.missingFields` описывает **тот комплект**, который отдан в этом же ответе
(`documentVersion` / `generatedAt`). Это не проверка готовности отчёта на сейчас.

- Каждый `POST .../generate` заново вычисляет замечания по актуальным исходным данным. Сохранённый
  снимок **никогда** не блокирует повторное формирование.
- Штатный сценарий: увидеть замечание → исправить данные → сформировать заново → замечание исчезает
  из нового комплекта.
- Живая готовность отчёта — `GET /api/pek/reports/{id}/readiness`.

### Состав ZIP

`data.files` — манифест, точно совпадающий с фактическим набором entry в архиве.

Протоколы кладутся как `Протоколы/{номер}_{protocolId}.pdf`. `protocolId` обязателен для
уникальности: очистка имени заменяет запрещённые в пути символы, из-за чего разные номера
схлопываются в одну строку (`A/1` и `A:1` → `A_1`). Пустой или пробельный номер даёт основу
`protocol`, различие обеспечивает id. Кириллица сохраняется как есть (архив пишется в UTF-8).
Повторяющийся путь внутри комплекта — ошибка (`PEK_PACKAGE_DUPLICATE_ENTRY`), а не молчаливая замена.

## 2. Реестры программы

Общее для всех трёх реестров (`emission-sources`, `discharge-sources`, `waste-items`):

| Метод | Путь | `If-Match` |
|---|---|---|
| GET | `/api/pek/programs/{programId}/{реестр}` | — |
| POST | `/api/pek/programs/{programId}/{реестр}` | — |
| PUT | `/api/pek/programs/{programId}/{реестр}/{id}` | версия **дочерней записи** |
| DELETE | `/api/pek/programs/{programId}/{реестр}/{id}` | версия **дочерней записи** |

- GET — `PEK_VIEW`; мутации — `PEK_PROGRAM_EDIT`, плюс tenant-scoping по программе.
- Мутации разрешены только пока программа редактируема; иначе 409 `PEK_PROGRAM_NOT_EDITABLE`
  (чтение остаётся доступным).
- `If-Match: 0` валиден; отсутствие — 400 `VERSION_REQUIRED`; расхождение — 409 `PEK_VERSION_CONFLICT`.
- Любая мутация увеличивает `contentRevision` программы и **каскадом** — всех её отчётов, поэтому
  ранее сформированные документы и комплекты становятся устаревшими.

Имена полей — как в `PekProgramSectionDtos`, без изменений.

### Числа и валидация

Дробные величины передаются **строками** (`"35.5"`), пустые необязательные поля — `null`.
Строка разбирается в `BigDecimal`; допускается запятая как разделитель.

| Правило | Ответ |
|---|---|
| нечисловая строка | 400, поле названо в сообщении |
| отрицательная величина | 400 |
| `cleaningEfficiencyPercent > 100` | 400 |
| `receiverBin` не 12 цифр | 400 |
| пустой обязательный `code` / `name` | 400 |

### Удаление вида отхода

Вид отхода, по которому уже введено движение за какой-либо период, удалить нельзя:
409 `PEK_WASTE_ITEM_HAS_MOVEMENTS`.

## 3. Движение отходов (в разрезе отчёта)

| Метод | Путь | `If-Match` |
|---|---|---|
| GET | `/api/pek/reports/{reportId}/waste-movements` | — |
| POST | `/api/pek/reports/{reportId}/waste-movements` | версия строки — только если она уже есть |
| DELETE | `/api/pek/reports/{reportId}/waste-movements/{id}` | версия строки |

POST — **upsert по паре (reportId, wasteItemId)**: одна строка на вид отхода за период.

- строки ещё нет → заголовок не передаётся, создаётся новая;
- строка есть → передаётся её `version`; отсутствие — 400 `VERSION_REQUIRED`, расхождение — 409
  `PEK_VERSION_CONFLICT`;
- гонка двух вставок по одной паре → 409 `PEK_WASTE_MOVEMENT_DUPLICATE` (уникальное ограничение
  `uk_pek_waste_movement_report_item`).

`wasteItemId` обязан принадлежать программе **этого** отчёта, иначе 404. Мутации разрешены только
пока отчёт редактируем (`DRAFT` / `COLLECTING` / `RETURNED`), иначе 409 `PEK_REPORT_NOT_EDITABLE`.
Любая мутация увеличивает `contentRevision` отчёта.

### Сходимость баланса

Расхождение не исправляется молча. Ответ всегда содержит:

- `closingBalance` — то, что ввёл пользователь (именно это попадёт в отчёт);
- `impliedClosingBalance` — расчёт `остаток на начало + образование − передача − удаление`;
- `reconciles` — `false`, если они не совпадают.

В официальном документе несходящиеся виды отходов дополнительно перечисляются отдельной строкой.
