# Оставшиеся backend-ограничения ПЭК

Источник проверки: `eco-master (18).zip`, контроллеры, DTO, security expressions и сервисы ПЭК проверены 06.08.2026. В документ включены только подтверждённые ограничения.

## 1. LABORATORY и доступные действия отчёта

`PekSecurityExpressions.PEK_REPORT_COLLECT` разрешает сбор роли `LABORATORY`, но `PekReportService.availableActions()` не считает эту роль автором отчёта и возвращает для неё `collect=false`, `edit=false`, `matchSources=false`.

Frontend соблюдает приоритет `availableActions`, поэтому кнопка сбора для `LABORATORY` появится только после согласования backend-ответа. Ослаблять это ограничение на frontend небезопасно.

## 2. Защита источников закрытого отчёта

Backend-методы ручного сопоставления, исключения и восстановления источника проверяют роль, но не проверяют статус отчёта. Прямой API-вызов может изменить источник отчёта со статусом `READY_FOR_REVIEW`, `APPROVED` или `ARCHIVED`.

Frontend скрывает эти действия по сочетанию статуса, разрешения и `availableActions`, но backend также должен запретить mutation и возвращать `PEK_REPORT_NOT_EDITABLE`.

## 3. История отчёта

Endpoint `GET /api/pek/reports/{id}/history` отсутствует. Доступна только история программы `GET /api/pek/programs/{id}/history`.

Frontend не показывает фиктивную вкладку истории отчёта. Для timeline требуется серверный audit endpoint.

## 4. Причина возврата отчёта

`POST /api/pek/reports/{id}/return` принимает обязательный `reason`, однако `ReportResponse` не содержит `returnInfo`, причины, автора или даты возврата. Сервис не сохраняет эти сведения в доступную frontend историю.

Frontend показывает статус `RETURNED` и текущую версию, но полные сведения о возврате невозможно восстановить после перезагрузки.

## 5. Расширенный DTO источника

`ReportSourceItem` содержит идентификаторы протокола и результата, название показателя, единицу, связь с позицией/показателем программы, статус сопоставления, версии и сведения об исключении.

В DTO отсутствуют:

- дата и статус протокола;
- исходное числовое значение результата;
- норматив и признак превышения;
- место и дата отбора/измерения;
- методика и лаборатория.

Frontend показывает все доступные поля и не подставляет фиктивные значения. Для полной таблицы и контекста диалога требуется расширить response DTO.

## 6. Dashboard

Dashboard v18 не возвращает `returnedReportCount`, `unmatchedSourceCount`, `ambiguousSourceCount`, `staleSourceCount`. Несколько KPI, которые сервис фактически не рассчитывает, возвращаются обязательным нулём, поэтому клиент не может отличить реальный ноль от состояния «не рассчитано».

Frontend не выдаёт такие нули за фактические показатели. Для точного отображения backend должен возвращать nullable-поля либо явный статус доступности метрики.

## 7. Company scope настроек

`GET/PUT /api/pek/settings` не принимает `companyId`; организация определяется активным membership через `OrganizationResolver`. Frontend изолирует cache по текущему scope, но явный выбор компании на странице настроек невозможен без backend-параметра или подтверждённого механизма переключения активной организации.

## 8. Readiness при утверждении

Frontend повторно запрашивает readiness перед approve. Backend `approve` должен также самостоятельно проверять readiness, поскольку клиентская проверка не защищает прямой API-вызов и между GET readiness и POST approve состояние может измениться.
