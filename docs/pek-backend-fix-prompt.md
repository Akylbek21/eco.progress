# Промпт для исправления бэкенда ПЭК

Работай в серверном репозитории ECOPROGRESS (Java 21 / Spring Boot). Базовая версия для аудита — `eco-master (11).zip`, проверенная 09.09.2026. Исправь перечисленные проблемы ПЭК, добавь регрессионные тесты и обнови API-контракт. Сначала сверь текущий код: часть проблем могла быть уже исправлена. Изменяй только бэкенд. Не запускай операции на рабочей базе и не публикуй изменения.

## Контекст уже внесённых изменений фронтенда

- Действия источников отчёта теперь используют `availableActions.matchSources`, как текущий `PekReportService`. Не переименовывай этот ключ в `manageSources`.
- При отсутствии комплекта UI поддерживает `ReportResponse.availableActions.generatePackage`. Для старого сервера, где этот ключ отсутствует, временно использует серверный `generateDocument`. Явный `generatePackage=false` не подменяется этим fallback.
- Для существующего комплекта используется `PackageResponse.availableActions.generatePackage`. Генерация скрыта для `SIGNED` / `ARCHIVED`.
- Старый список `missingFields` больше не блокирует кнопку повторного формирования: пользователь может исправить исходные данные и повторить запрос.
- Добавлены формы существующих `PekInventoryController` endpoints: источники выбросов, источники сбросов, виды отходов, движение отходов. Дробные величины отправляются JSON-строками; пустые необязательные поля — null. PUT/DELETE передают версию дочерней записи в If-Match. Движение отходов сохраняется через POST-upsert; для существующей строки передаётся её версия, для новой заголовок отсутствует.

## 1. Разрешение первого формирования комплекта

В `PekReportService.availableActions()` отсутствует `generatePackage`. При первом `GET /api/pek/reports/{id}/package` возвращается 404, поэтому флаг нельзя получить из PackageResponse.

Добавь boolean `generatePackage` в `ReportResponse.availableActions`, включая отчёты без ранее созданного комплекта. Вынеси вычисление прав/статусов в общий сервис или метод и используй его также в `PekReportPackageService.dto()` и проверке выполнения операции. Не вычисляй действия только по роли: соблюдай текущий tenant scope, permissions и допустимость генерации документа. Сохрани совместимость остальных ключей и формат `ApiResponse`.

Тесты: первый комплект для разрешённого редактора; отсутствие прав; чужая компания; явное false для недопустимого статуса.

## 2. Согласовать генерацию комплекта со статусами и версиями

Сейчас `PekReportPackageService.dto()` возвращает `generatePackage=true` по роли даже в SIGNED/ARCHIVED, но `generate()` вызывает `finalDocs.generatePdf()`, запрещённый для этих статусов через `requireRegenerationAllowed` с кодом `PEK_REPORT_DOCUMENT_LOCKED`.

В рамках совместимого исправления возвращай false для SIGNED/ARCHIVED и запрещай прямой запрос. Не перегенерируй подписанный документ. Не меняй жизненный цикл отчёта без отдельного требования. Если продукту впоследствии понадобится сборка ZIP после подписания, реализуй отдельный явно согласованный путь с использованием существующего подписанного артефакта; текущий фронт блокирует генерацию в этих статусах.

`PekReportPackageController.generate()` сейчас не принимает If-Match, хотя фронт передаёт текущую версию отчёта. Принимай обязательный If-Match с версией отчёта; сравнивай атомарно в транзакции до генерации/сохранения файлов. Для пропущенной версии возвращай VERSION_REQUIRED, для устаревшей — согласованный 409/412 с PEK_VERSION_CONFLICT. Не путай версию отчёта, documentVersion комплекта и contentRevision. Предотврати гонку двух генераций: уникальные версии комплекта, отсутствие незаметной перезаписи. Не ограничивайся сравнением версий без блокировки/атомарного механизма.

Тесты: SIGNED/ARCHIVED и прямой POST; If-Match=0; устаревшая/отсутствующая версия; две конкурентные генерации; отсутствие лишних записей/файлов при отказе.

## 3. Повторная генерация после устранения missingFields

`missingFieldsJson` — снимок замечаний прошлой генерации. `latest()` возвращает этот снимок. Сохрани его смысл и документируй, что это замечания сформированного комплекта, а не текущая проверка готовности.

Каждый POST /package/generate должен заново проверять актуальные исходные данные, не блокироваться сохранённым missingFields старого комплекта. Если требуется актуальная readiness — возвращай её отдельным полем/endpoint, не выдавай старый снимок за текущий результат.

Тест: создать комплект при отсутствии PDF протокола → прикрепить PDF → повторить генерацию → новый ZIP содержит PDF, соответствующее замечание исчезает.

## 4. Исключить тихую потерю протоколов внутри ZIP

В `PekReportPackageService.generate()` путь строится как `Протоколы/` + safe(protocolNumber) + `.pdf`, а `addStored()` использует `Map.put`. Разные номера `A/1` и `A:1` дают одинаковое имя `A_1.pdf`; второй файл заменяет первый.

Включай уникальный protocolId в имя, например `Протоколы/{safe(number)}_{id}.pdf`. Проверь также null/пустые номера. Не допускай молчаливой перезаписи: явно выявляй повторный путь. Сохрани безопасную обработку символов и Unicode. Проверь соответствие manifest/files фактическим ZIP entries.

Тесты должны распаковать ZIP и проверить наличие и байтовое содержимое двух разных PDF при совпавших очищенных именах, а также при пустых номерах.

## 5. Проверить новые используемые фронтом реестры

Маршруты уже существуют, не создавай дубли:

- GET/POST `/api/pek/programs/{programId}/emission-sources`, PUT/DELETE `/{id}`.
- GET/POST `/api/pek/programs/{programId}/discharge-sources`, PUT/DELETE `/{id}`.
- GET/POST `/api/pek/programs/{programId}/waste-items`, PUT/DELETE `/{id}`.
- GET/POST `/api/pek/reports/{reportId}/waste-movements`, DELETE `/{id}`.

Сохрани имена полей из `PekProgramSectionDtos`. Проверь запрет правок закрытых программ/отчётов, tenant isolation, принадлежность wasteItem программе отчёта, If-Match дочерней записи включая 0, отсутствие дубликатов пары reportId/wasteItemId при конкурентном upsert, запрет удаления используемого вида отхода. Проверь валидацию строк BigDecimal, отрицательных величин, процента очистки >100, БИН из 12 цифр. Расхождение баланса не исправляй молча: возвращай `reconciles` и `impliedClosingBalance`.

Проверь, что изменение реестров/движения отходов увеличивает нужную contentRevision и делает производные документы/комплекты устаревшими. Не считай все эти пункты уже обнаруженными дефектами: это критерии проверки существующей реализации.
