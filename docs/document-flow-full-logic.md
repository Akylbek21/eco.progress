# Документооборот EcoProgress — полная сквозная логика

Дата актуализации: 31.07.2026.

## 1. Назначение и границы модуля

Раздел «Документооборот» управляет внутренними, входящими и исходящими документами организации: созданием карточки, загрузкой файла, версиями, вложениями, маршрутами согласования и подписания, ЭЦП через NCALayer, внешним подписанием по защищённой ссылке, проверкой подписей, отзывом и архивом.

Главная сущность — `Document`. Организация-владелец определяется backend из JWT и активного организационного контекста. Клиент не должен получать доступ к документам другой организации только через подмену `organizationId` или `documentId`.

## 2. Участники

- Автор — создаёт и редактирует черновик, загружает файл, задаёт маршрут.
- Сотрудник-подписант — просматривает и подписывает назначенный ему документ либо отклоняет его.
- Представитель контрагента — подписывает как связанный представитель.
- Внешний подписант — работает без JWT по одноразовому token-scoped приглашению.
- Администратор организации — управляет контрагентами, участниками, доступом и подпиской в пределах организации.
- Администратор EcoProgress (`ADMIN`) — управляет тарифами, подписками и выдачей доступа.

Любая операция одновременно проверяет JWT/публичный токен, организацию, подписку, feature, permission, разрешение конкретного документа и его текущее состояние.

## 3. Вход в раздел и доступ

1. Пользователь открывает `/document-flow`.
2. Неавторизованный пользователь перенаправляется на `/login`.
3. Frontend вызывает `GET /api/document-flow/access`.
4. Backend возвращает `available`, `readOnly`, статус и срок подписки, тариф, features, permissions, limits, usage и доступные действия.
5. Если `available=false`, рабочий интерфейс не открывается. Пользователь видит тарифы и может отправить заявку через `POST /api/document-flow/access-requests`.
6. Если `available=true`, открывается dashboard.
7. Если `readOnly=true`, документы доступны для просмотра и скачивания, но все изменения и команды блокируются на frontend и повторно на backend.
8. Backend проверяет лимиты до изменения данных. Исчерпание лимита возвращает `409` или `422` с машинным кодом лимита и понятным сообщением.

Публичная страница тарифов `/document-flow/plans` доступна без рабочей подписки. Административные маршруты `/admin/document-flow/*` доступны только роли `ADMIN`.

## 4. Основные справочники

### Типы документов

`GET /api/document-flow/document-types` возвращает активные типы и для каждого типа определяет:

- допустимое направление: входящий, исходящий или оба;
- требуется ли контрагент;
- требуется ли подписание;
- необходимую тарифную feature;
- допустимые MIME-типы;
- максимальный размер основного файла.

Frontend использует конфигурацию для формы, но backend обязан повторить все проверки при создании и загрузке.

### Контрагенты

Контрагент содержит БИН, название, руководителя, адрес и контакты. Представители принадлежат конкретному контрагенту. Использованного в документах контрагента нельзя физически удалить: `DELETE` переводит его в архив. Архивный контрагент остаётся в старых документах, но не предлагается при создании нового.

## 5. Создание документа

Мастер `/document-flow/documents/new` выполняется в следующем порядке:

1. Выбор активного типа документа.
2. Выбор допустимого направления `INCOMING`, `OUTGOING` или `INTERNAL`.
3. Заполнение названия, описания и срока подписания.
4. Выбор контрагента, если он обязателен для типа.
5. Выбор основного файла. Проверяются MIME-тип, размер и непустое содержимое.
6. Если подписание обязательно — настройка маршрута.
7. Итоговая проверка всех полей и подтверждение.
8. `POST /api/document-flow/documents` создаёт `DRAFT`. Запрос содержит стабильный `Idempotency-Key`, поэтому повтор после сетевого сбоя не создаёт дубликат.
9. `POST /api/document-flow/documents/{id}/file` загружает основной файл и создаёт первую версию с SHA-256.
10. При необходимости `POST /api/document-flow/documents/{id}/signing-route` сохраняет маршрут.
11. После успеха открывается `/document-flow/documents/{id}`.

Создание считается завершённым только после успешной загрузки файла. Если карточка создана, а загрузка не удалась, backend сохраняет восстанавливаемый `DRAFT`; UI должен предложить повторить загрузку или удалить незавершённый черновик.

## 6. Жизненный цикл документа

```text
DRAFT
  ├─ подготовить ─> READY_FOR_SIGNING
  │                    └─ отправить ─> SENT_FOR_SIGNING
  │                                         ├─ часть подписей ─> PARTIALLY_SIGNED
  │                                         ├─ все обязательные подписи ─> SIGNED
  │                                         ├─ отклонение ─> REJECTED
  │                                         ├─ возврат ─> RETURNED_FOR_REVISION
  │                                         ├─ отмена автором ─> CANCELLED
  │                                         └─ истёк срок ─> EXPIRED
  └─ удалить черновик

RETURNED_FOR_REVISION ─ новая версия/новый маршрут ─> DRAFT
SIGNED ─ запрос отзыва ─> REVOCATION_REQUESTED ─ согласование ─> REVOKED
любой завершённый статус ─ архивирование ─> ARCHIVED
```

Backend является единственным источником истины для переходов и возвращает `availableActions`. Frontend показывает команду только при одновременном выполнении feature, permission, `DocumentPermissions`, `availableActions` и допустимого статуса.

### Подготовка к подписанию

`POST /documents/{id}/prepare-for-signing` принимает `expectedVersion` и атомарно проверяет:

- документ в редактируемом статусе;
- существует текущая версия файла;
- файл прошёл антивирусную/форматную проверку;
- маршрут существует и валиден;
- все обязательные назначения заполнены;
- срок подписания не истёк;
- версия карточки не изменилась конкурентно.

После подготовки текущая версия и маршрут блокируются от изменения, статус становится `READY_FOR_SIGNING`.

### Отправка

`POST /documents/{id}/send-for-signing` активирует маршрут, переводит документ в `SENT_FOR_SIGNING`, делает доступным первый шаг и создаёт уведомления. Для внешних назначений backend создаёт случайный одноразовый токен с ограниченным сроком, хранит только его hash и отправляет ссылку адресату.

## 7. Маршруты подписания

- `SEQUENTIAL` — шаги открываются строго по порядку. Следующий шаг недоступен, пока предыдущий не набрал `requiredCount`.
- `PARALLEL` — все назначения доступны одновременно; завершение определяется общим правилом маршрута.
- `MIXED` — шаги идут последовательно, а назначения внутри активного шага выполняются параллельно.

У каждого шага есть `requiredCount`: число должно быть от 1 до количества назначений. Назначение бывает `ORGANIZATION_MEMBER`, `COUNTERPARTY_REPRESENTATIVE` или `EXTERNAL`. Несколько подписантов и типы маршрута дополнительно ограничиваются тарифными features.

Перед сохранением backend проверяет существование пользователя/представителя, принадлежность нужной организации или контрагенту, уникальность назначения, корректность email внешнего подписанта и отсутствие пустых шагов.

## 8. Внутреннее подписание через NCALayer

1. Подписант открывает карточку и получает актуальный маршрут и назначения.
2. Backend разрешает подпись только для активного назначения текущего пользователя.
3. `GET /documents/{id}/signing-data` возвращает `documentId`, `versionId`, `assignmentId`, hash и канонические байты/данные для подписи.
4. Browser передаёт данные в NCALayer. Закрытый ключ, пароль и PKCS#12 никогда не отправляются в EcoProgress.
5. NCALayer возвращает CMS.
6. Frontend отправляет только allow-list: `documentId`, `versionId`, `assignmentId`, `cms`, уникальный `clientRequestId`.
7. Backend проверяет CMS, сертификат, срок действия, цепочку доверия, отзыв сертификата, ИИН/БИН и соответствие подписи hash заблокированной версии.
8. Повтор с тем же `clientRequestId` возвращает прежний результат, не создавая вторую подпись.
9. Назначение становится `SIGNED`; backend пересчитывает шаг и маршрут. Документ переходит в `PARTIALLY_SIGNED` либо `SIGNED`.

Подпись над старой версией, чужим назначением или уже завершённым назначением отклоняется.

## 9. Внешнее подписание

1. Адресат открывает `/public/document-flow/sign/{token}` без JWT.
2. `GET /api/public/document-flow/signing/{token}` проверяет hash токена, срок, статус назначения и возвращает только данные этого приглашения.
3. `GET .../{token}/file` отдаёт зафиксированную версию документа.
4. `POST .../{token}/viewed` идемпотентно фиксирует просмотр.
5. Для подписи public API должен выдать token-scoped challenge с `versionId`, `assignmentId`, hash/байтами и затем принять CMS через `POST .../{token}/sign`.
6. Для отказа обязательна причина: `POST .../{token}/reject`.
7. После подписи/отказа/истечения срока токен становится непригодным для повторной операции.

Токен нельзя сохранять в localStorage, отправлять в аналитику или логи и показывать другим назначениям.

## 10. Отклонение, возврат и отмена

- `reject` завершает назначение отказом и переводит документ в `REJECTED`, если правила маршрута больше не позволяют набрать обязательное количество подписей.
- `return-for-revision` переводит документ в `RETURNED_FOR_REVISION`; причина обязательна. Активные приглашения отзываются.
- `cancel-signing` доступен уполномоченному автору до полного подписания; причина фиксируется, приглашения аннулируются, статус становится `CANCELLED`.
- После доработки создаётся новая версия и при необходимости новый маршрут. Старые подписи сохраняются в аудите, но не считаются подписями новой версии.

## 11. Версии и вложения

Основной файл имеет версии. Каждая версия хранит номер, исходное имя, MIME-тип, размер, SHA-256, автора и дату. Только одна версия текущая. После подготовки к подписанию текущая версия блокируется. Новая версия разрешена только в редактируемом статусе и при feature `VERSIONING`.

Вложения не являются основным подписываемым файлом, если это явно не определено backend-политикой. Их можно добавлять и удалять только до блокировки документа. Скачивание выполняется через авторизованный endpoint; storage key никогда не раскрывается клиенту.

## 12. Проверка и подписанный пакет

`POST /documents/{id}/signatures/verify-all` повторно проверяет все CMS и сертификаты. `GET /documents/{id}/verification-report` возвращает структурированный отчёт. Для `SIGNED` backend формирует ZIP через `GET /documents/{id}/signed-package`, включающий:

- подписанную версию документа;
- CMS-файлы подписей;
- сведения о сертификатах и результатах проверки;
- маршрут и временные отметки;
- машиночитаемый манифест с SHA-256.

ZIP создаёт только backend. Frontend не собирает юридически значимый пакет самостоятельно.

## 13. Отзыв подписанного документа

1. Для `SIGNED` пользователь с permission `REVOKE_SIGNATURE` и feature `REVOCATION` создаёт запрос с обязательной причиной.
2. Запрос получает `DRAFT`.
3. Команда `send` переводит его в `PENDING`, документ — в `REVOCATION_REQUESTED`.
4. Уполномоченная сторона выполняет `approve` или `reject` с комментарием.
5. При одобрении запрос получает `APPROVED`, документ — `REVOKED`; при отказе запрос становится `REJECTED`, документ возвращается в `SIGNED`.
6. Автор может отменить нерассмотренный запрос; документ возвращается в `SIGNED`.

Отзыв не удаляет документ, версии и подписи, а добавляет новый юридически значимый факт.

## 14. Список, dashboard и поиск

Dashboard показывает общее количество, разбивку по статусам и направлениям. Список документов фильтруется на backend по направлению, типу, статусу, контрагенту, автору, подписанту, необходимости моей подписи, просрочке, датам создания/срока и строке поиска. Пагинация и сортировка выполняются на сервере.

Карточка списка показывает номер, название, тип, направление, контрагента, автора, срок, статус, прогресс обязательных подписей и признак «требуется моя подпись».

## 15. Удаление и архив

- Физически удалить через пользовательский API можно только `DRAFT`, если документ не имеет юридически значимых действий.
- Подписанные, отклонённые, отменённые, отозванные и истёкшие документы не удаляются, а архивируются отдельной командой.
- `ARCHIVED` остаётся доступным для поиска, скачивания, проверки и аудита в режиме только чтения.
- Retention и окончательное уничтожение реализуются отдельной административной политикой, а не кнопкой пользователя.

## 16. Аудит и уведомления

Backend неизменяемо фиксирует: создание и редактирование, загрузку/скачивание, hash версии, изменение маршрута, подготовку, отправку и просмотр приглашения, подпись и проверку сертификата, отказ/возврат/отмену, отзыв, архивирование, администратора действия и correlation ID.

Уведомления отправляются при назначении, открытии следующего шага, приближении срока, просрочке, подписи, отказе, возврате, завершении и отзыве. Ошибка уведомления не должна откатывать уже зафиксированную бизнес-операцию; она попадает в retry/outbox.

## 17. Ошибки и конкурентность

- `400` — неверный формат запроса.
- `401` — отсутствует/истёк JWT или public token.
- `403` — нет feature, permission или доступа к организации/документу.
- `404` — сущность не найдена либо скрыта tenant-политикой.
- `409` — недопустимый переход статуса, повторная операция, конфликт версии или исчерпанный лимит.
- `413` — файл превышает допустимый размер.
- `415` — неподдерживаемый MIME-тип.
- `422` — бизнес-валидация маршрута, сертификата или обязательных полей.

Команды создания, подписи и выдачи доступа идемпотентны. Для изменения карточки и подготовки используется optimistic locking (`version`/`expectedVersion`). Все ответы об ошибке содержат безопасное сообщение и `correlationId`, но не stack trace и не внутренние storage paths.

## 18. Администрирование

EcoProgress ADMIN может создавать и изменять тарифы, включать features, задавать лимиты, выдавать доступ организации, продлевать, приостанавливать, восстанавливать и отзывать подписку, менять тариф и entitlement. Каждая операция требует причины, аудируется и не даёт администратору неявного доступа к содержимому документов организации.

Статусы подписки влияют на доступ так:

- `TRIAL`, `ACTIVE` — работа по тарифу;
- `GRACE_PERIOD` — политика backend определяет полный или read-only доступ;
- `SUSPENDED`, `EXPIRED`, `CANCELLED` — только чтение либо полный запрет согласно `AccessContext`;
- `PENDING` — заявка ещё не активирована.

## 19. Текущая последовательность API

```text

```

## 20. Известные блокеры текущей реализации

До полноценного production E2E необходимо закрыть следующие backend gaps:

1. Public invitation не возвращает безопасные `assignmentId`, `versionId` и signing challenge, поэтому внешняя CMS-подпись сейчас не может быть корректно сформирована.
2. Фильтр «Мне на подпись», `signedCount`, `requiredCount` и `requiresMySignature` в списке возвращаются заглушками.
3. Нет endpoint скачивания вложения.
4. Backend объявляет действие `ARCHIVE`, но отдельного archive endpoint нет.
5. Нет read endpoint журнала аудита.
6. Нет серверного поиска контрагентов по БИН/названию.
7. Нет справочника участников организации для безопасного выбора внутреннего подписанта; UI требует ручной `userId`.
8. Multi-organization context не возвращает список организаций и выбранный `organizationId`.
9. Version/attachment API должен возвращать безопасные DTO вместо JPA entities со storage fields.

Модуль нельзя считать полностью завершённым, пока эти пункты не закрыты и не пройден E2E с реальной БД, NCALayer, внутренним и внешним подписантом.

## 21. Минимальные критерии приёмки

- Пользователь без подписки не попадает в рабочую область и может подать заявку.
- Черновик создаётся без дублей при повторе запроса.
- Недопустимый файл отклоняется и frontend, и backend.
- Последовательный, параллельный и смешанный маршруты соблюдают порядок и `requiredCount`.
- Нельзя подписать чужое назначение или неактуальную версию.
- Все обязательные подписи атомарно переводят документ в `SIGNED`.
- Отказ, возврат, отмена и отзыв имеют обязательную причину и корректный переход статуса.
- Public token не раскрывает другие документы и не работает после использования/истечения.
- Подписанный ZIP и verification report воспроизводимо проверяются по SHA-256 и CMS.
- Tenant isolation, read-only режим, permissions, features и limits проверены интеграционными тестами.
- История содержит каждое юридически значимое действие с пользователем, временем и correlation ID.
