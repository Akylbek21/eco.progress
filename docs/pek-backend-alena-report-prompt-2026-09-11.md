# Промпт для backend: полный путь ПЭК → отчёт

Работай в актуальном серверном репозитории ECOPROGRESS (Java 21 / Spring Boot), а не в локальной аудит-копии frontend-репозитория `.audit-pek`. Цель: обеспечить проверяемый сквозной сценарий для программы ПЭК и квартального отчёта без ослабления readiness, tenant isolation, прав и optimistic locking.

Не работай с production-БД и не публикуй изменения. Используй тестовую БД и файловое хранилище. Сначала сверь текущую реализацию: часть требований может уже присутствовать. Не создавай параллельные DTO или endpoints, если канонический маршрут уже существует.

## 1. Сделать readiness единственным источником процента готовности программы

Сейчас подробная проверка `PekProgramReadinessService.evaluate()` возвращает `progressPercent`, но `PekProgramService` отдельно рассчитывает `readinessPercent` только по пяти полям. Из-за этого одна программа показывает 33% в readiness и 40% в списке/структуре.

- Удали или перестань использовать старый пятифакторный расчёт `PekProgramService.readinessPercent(...)`.
- В `ProgramResponse.readinessPercent` возвращай тот же `progressPercent`, который вычисляет `PekProgramReadinessService`.
- `GET /api/pek/programs`, `GET /api/pek/programs/{id}` и `GET /api/pek/programs/{id}/readiness` должны давать одинаковый процент для одной ревизии данных.
- Не убирай блокирующие проверки и не округляй их разными алгоритмами.
- Учти производительность списка: не допускай N+1 запросов на каждую программу; при необходимости сделай агрегированный/batch-расчёт.

Тесты: программа с 8 блокерами; полностью готовая программа; неприменимые направления мониторинга; одинаковый процент в list/detail/readiness.

## 2. Согласовать `ReportCreationContext` с frontend-контрактом

Frontend ожидает от `GET /api/pek/reports/creation-context` поля:

```json
{
  "company": { "id": 14, "name": "ТОО \"АЛЕАНА СЕРВИС\"" },
  "object": { "id": 14, "name": "Основной объект - ТОО \"АЛЕАНА СЕРВИС\"" },
  "periodStart": "2026-07-01",
  "periodEnd": "2026-09-30",
  "submissionDueDate": "2026-11-01",
  "regulationVersion": "PEK_RULES_250_2026_59",
  "templateVersion": "v2-2026",
  "programs": [],
  "selectedProgramId": null,
  "duplicateReportId": null,
  "warnings": [],
  "blockingReasons": []
}
```

Текущий `ReportCreationContext` аудит-копии не содержит `submissionDueDate`, `regulationVersion`, `templateVersion`, поэтому UI показывает «Не установлен» и «— / —».

- Добавь эти поля в канонический response DTO и OpenAPI.
- Если найдена ровно одна подходящая ACTIVE-программа, версии формы/НПА бери из неё.
- Срок рассчитывай сервером через `PekSubmissionDeadlineService` по типу отчёта, редакции НПА и окончанию периода.
- Если ACTIVE-программы нет, не выдумывай версии: возвращай null и явный blocker.
- Проверяй, что ACTIVE-программа принадлежит компании/объекту и полностью покрывает период.
- Сохрани защиту от дубликата отчёта за тот же program/object/periodKey.

Тесты: Q1–Q4, годовой период, граница действия программы, отсутствие/несколько ACTIVE-программ, duplicate, чужая компания.

## 3. Миграция legacy-программ на актуальный шаблон

Для существующих `v1-legacy` программ нужен явный безопасный сценарий актуализации:

- Добавь отдельное действие/endpoint re-template только для DRAFT или RETURNED.
- Действие должно выбрать актуальную запись `PekRegulationVersionService.current()`, обновить `regulationVersion` и `templateVersion`, увеличить `contentRevision` и записать аудит.
- Не обновляй APPROVED/ACTIVE программы молча и не меняй исторические отчёты.
- Если структура новой формы требует дополнительных данных, после re-template readiness должен показать конкретные новые блокеры.
- Верни действие в `availableActions`, чтобы frontend не вычислял право по роли.

Тесты: DRAFT/RETURNED разрешены; UNDER_REVIEW/APPROVED/ACTIVE/ARCHIVED запрещены; If-Match обязателен; устаревшая версия даёт 409/412; аудит и contentRevision обновлены.

## 4. Полноценная фиксация официальной сдачи

Сейчас `POST /api/pek/reports/{id}/submit` без request body фиксирует только статус и `submittedAt`. Для рабочего документооборота добавь отдельный DTO официальной сдачи:

```json
{
  "submittedAt": "2026-10-20T10:30:00+05:00",
  "registrationNumber": "KZ-PEK-2026-00123",
  "submissionMethod": "ECO_PORTAL",
  "confirmationFileId": 12345,
  "comment": "Принято порталом"
}
```

- Согласуй обязательность полей с владельцем продукта; не принимай произвольные enum-значения.
- Подтверждающий файл должен принадлежать той же компании и быть разрешённого типа/размера.
- Сдача разрешена только после утверждения и подписания актуального официального документа.
- Проверяй If-Match, права, tenant scope, актуальность document/content revision и наличие подписи.
- Сохраняй реквизиты в отдельных колонках/сущности и возвращай их в `ReportResponse`.
- Старый вызов без body либо версионируй, либо отклоняй понятной контрактной ошибкой; не создавай фиктивные реквизиты.
- Записывай аудит без содержимого ЭЦП и других секретов.

Тесты: успешная сдача; неподписанный/устаревший документ; чужой файл; повторная сдача; version conflict; отсутствие прав; round-trip всех реквизитов.

## 5. Подтвердить сквозной сценарий на тестовом стенде

Подготовь fixtures без использования реальных данных клиента:

1. компания и объект;
2. заполненная программа;
3. направления мониторинга, точки/источники, позиции контроля, показатели, методы и периодичность;
4. внутренние проверки, QA/QC, аварийные процедуры, ответственность;
5. разрешение, если оно применимо;
6. DRAFT → UNDER_REVIEW → APPROVED → ACTIVE с разными maker/checker пользователями;
7. создание квартального отчёта;
8. сбор и сопоставление протоколов;
9. plan/fact, превышения и корректирующие мероприятия;
10. генерация актуального официального документа;
11. подпись тестовой ЭЦП/заглушкой криптопровайдера;
12. официальная сдача и повторное открытие сохранённых реквизитов.

Проверь tenant isolation, resource-level `availableActions`, If-Match=0, stale document/content revision, повторные запросы и аудит каждого перехода.

## Приёмка

- Все профильные unit/API/integration тесты ПЭК проходят.
- OpenAPI и примеры response обновлены.
- List/detail/readiness возвращают одинаковую готовность.
- Creation-context возвращает срок и версии либо объяснённые null + blockers.
- Нельзя создать отчёт без ACTIVE-программы или вне её периода.
- Нельзя подписать/сдать устаревший документ.
- Реквизиты официальной сдачи сохраняются и читаются повторно.
- Предоставь список миграций и изменённых файлов, результаты тестов и отдельно — всё, что не было проверено фактически.
