# Проверка ПЭК — 09.09.2026

Проверены серверные исходники из `C:\Users\akylbek\Downloads\eco-master (11).zip` и интерфейс в текущей рабочей папке. Архив распакован в `.audit-pek/eco-master`. Старые отчёты из репозиториев не считались доказательством исправности текущей версии. Код приложения не изменялся.

## Итог

Полную работоспособность ПЭК подтвердить нельзя. Найдены шесть проблем по исходному коду, включая два расхождения флагов API, блокирующих действия интерфейса. Это аудит кода и автоматических тестов, а не завершённая сквозная проверка работающего сервера.

## Подтверждённые проблемы

### 1. P1 — недоступны действия с источниками отчёта

Сервер `PekReportService.java:869` возвращает `availableActions.matchSources`. Интерфейс `src/features/pek/pages/PekReportWorkspacePage.tsx:265` проверяет `availableActions.manageSources`. Маппер `responseMappers.ts:164` переносит флаги без переименования.

У редактора отчёта даже при `matchSources=true` отсутствуют кнопки ручного сопоставления, исключения и восстановления источника (`PekReportWorkspacePage.tsx:318`). Требуется согласовать имя флага с сервером и проверить положительный сценарий на реальном формате ответа.

### 2. P1 — нельзя впервые сформировать комплект ZIP через интерфейс

Когда комплект отсутствует, сервер отвечает 404, `pekApi.getReportPackage` преобразует его в `null`. В этой ветке `PekReportPackageCard.tsx:61` показывает кнопку только при `report.availableActions.generatePackage=true`. `PekReportService.availableActions()` такого ключа не возвращает. Ключ существует только в ответе уже созданного комплекта (`PekReportPackageService.java:206`).

Требуется возвращать доступность первого формирования вместе с отчётом; проверять роль и допустимость генерации на сервере.

### 3. P1 — отсутствует интерфейс для серверных реестров источников и движения отходов

`PekInventoryController.java` предоставляет CRUD `/programs/{programId}/emission-sources`, `/discharge-sources`, `/waste-items`, а также чтение, сохранение и удаление `/reports/{reportId}/waste-movements`. В `src` нет вызовов этих маршрутов. Отдельные направления мониторинга «Источники выбросов» и «Отходы» не заменяют эти реестры.

Пользователь не может через данный интерфейс заполнить эти серверные сущности. Генераторы программы и официального отчёта используют соответствующие таблицы; при отсутствии данных они останутся незаполненными. Требуются API-методы, формы, таблицы и обработка версий для этих сущностей.

### 4. P2 — старые замечания комплекта блокируют повторную генерацию

`PekReportPackageService` сохраняет `missingFieldsJson` при генерации и возвращает сохранённый список в `latest()`. `PekReportPackageCard.tsx:92` отключает кнопку при `missingFields.length > 0`.

Сценарий: сформировать комплект, когда у протокола нет PDF; позже добавить PDF; вернуться к комплекту. Сохранённое замечание остаётся, кнопка повторной генерации отключена, хотя именно генерация должна пересчитать список. Требуется разрешить повторное формирование либо получать актуальную проверку готовности отдельно.

### 5. P2 — комплект предлагает генерацию для подписанного/архивного отчёта, но сервер её запрещает

`PekReportPackageService.java:206` вычисляет `generatePackage` только по роли. Формирование вызывает `finalDocs.generatePdf()` (`:99`), где `requireRegenerationAllowed` запрещает `SIGNED` и `ARCHIVED` с `PEK_REPORT_DOCUMENT_LOCKED` (`docgen/PekReportDocumentGenerationService.java:344`).

При существующем комплекте и отсутствии замечаний интерфейс может показывать доступную кнопку, которая завершится конфликтом. Требуется согласовать флаг со статусом; если бизнес-процесс требует комплект после подписания, использовать существующий подписанный документ вместо его повторного формирования.

### 6. P2 — возможна потеря PDF протокола внутри ZIP при совпадении очищенных имён

`PekReportPackageService.java:107` строит имя только из `safe(protocolNumber)`. Метод `safe` заменяет специальные символы на `_`, а `addStored` делает `files.put(name, ...)` (`:166`). Разные номера `A/1` и `A:1` превращаются в один путь; второй PDF заменяет первый в Map без ошибки. Это условный сценарий по коду, не утверждение о наличии таких номеров в рабочей базе.

Требуется включить уникальный ID протокола в имя файла или явно обрабатывать коллизии.
