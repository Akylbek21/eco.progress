# Аудит: программа ПЭК, отчёт ПЭК и протоколы

Дата: 2026-09-16  
Объект: `eco-master (21).zip`, backend Spring Boot 4 / Java 21

## Итог

Функциональная модель трёх модулей в целом зрелая: реализованы статусы и проверки переходов, optimistic locking, разграничение компаний, сбор протоколов в отчёт, readiness, версии документов, подписание и фиксация официальной сдачи. В проекте есть большой набор интеграционных тестов.

До production-приёмки рекомендовано устранить 2 критичных/высоких риска и восстановить воспроизводимый тестовый запуск.

## Найденные проблемы

### P0 — production создаёт ADMIN с общеизвестным паролем

`DataSeeder` является безусловной `@Configuration`, запускается во всех профилях и при пустой таблице пользователей создаёт:

- `admin@ecoprogress.kz / admin123`;
- несколько staff-аккаунтов с паролем `demo123`;
- клиентский аккаунт с паролем `demo123`.

Файлы: `src/main/java/kz/eco/config/DataSeeder.java:35`, `:91-105`, `:141-168`.

Риск: первый запуск новой production-БД немедленно создаёт известную административную учётную запись. Это прямой захват системы через штатный login endpoint.

Рекомендация: включать seeder только в `local`/`dev`/`test` через `@Profile`; для production создавать первого администратора отдельной одноразовой процедурой с уникальным секретом и обязательной сменой пароля. Добавить тест, что `DataSeeder` отсутствует в production context.

### P1 — Windows Maven Wrapper неработоспособен

`mvnw.cmd` обращается к `(Get-Item $MAVEN_M2_PATH).Target[0]`. Для обычной директории `Target == null`, из-за чего PowerShell падает с `Cannot index into a null array`, а wrapper завершает работу сообщением `Cannot start maven from wrapper`.

Файл: `mvnw.cmd:91-96`.

Воздействие: на чистой Windows-машине нельзя выполнить обязательные `test/package`; в архиве нет готовых Surefire-результатов. Системный Maven также не входит в поставку.

Рекомендация: заменить проверку на null-safe вариант либо восстановить официальный Maven Wrapper 3.3.4; затем выполнить полный `mvnw.cmd test` в CI на Windows и Linux.

### P1 — административный JWT хранится в `localStorage`

Встроенная страница настройки ПЭК сохраняет bearer token в `localStorage` (`pek_admin_token`) и использует его для глобальных административных операций.

Файл: `src/main/resources/static/pek-admin/index.html:163-168`, `:193-206`.

Риск: любая XSS-уязвимость на том же origin позволяет похитить ADMIN/DIRECTOR JWT (TTL по умолчанию 24 часа). Для административного интерфейса последствия особенно высоки.

Рекомендация: перейти на `HttpOnly + Secure + SameSite` cookie/BFF-сессию либо, как минимум, хранить access token только в памяти, сократить TTL, применить строгий CSP и убрать inline script.

### P2 — схема production управляется одновременно Flyway и Hibernate

В docker-профиле установлено `spring.jpa.hibernate.ddl-auto=update`, при этом присутствует длинная цепочка Flyway-миграций. Комментарии самих миграций уже фиксируют расхождения между физической схемой, Hibernate и Flyway.

Файл: `src/main/resources/application-docker.properties:9`; примеры: `V16__repair_protocol_module_schema.sql`, `V108__users_password_setup_hardening.sql`.

Риск: неповторяемая схема между окружениями, скрытые изменения при старте, сложный rollback и вероятность отказа именно модулей ПЭК/протоколов после обновления.

Рекомендация: в production использовать `ddl-auto=validate`, все изменения проводить только Flyway; добавить проверку миграции с пустой БД и с копией предыдущей production-схемы.

### P2 — API допускает молчаливое игнорирование неизвестных полей

Во многих request DTO протоколов используется `@JsonIgnoreProperties(ignoreUnknown = true)`.

Файл: `src/main/java/kz/eco/protocol/dto/ProtocolApiDtos.java` (много request records).

Риск: опечатка или рассинхронизация frontend/backend приводит к успешному HTTP-ответу при фактической потере входного поля. Для лабораторных результатов и юридически значимых документов это опаснее явной ошибки 400.

Рекомендация: для mutation DTO запретить неизвестные поля; совместимость обеспечивать явными aliases/versioned DTO. Добавить contract-тесты на отклонение неизвестных юридически значимых полей.

### P3 — аутентификация API защищена глобально, но fallback вне API открыт

`SecurityConfig` корректно требует аутентификацию для `/api/**`, но завершает правила `anyRequest().permitAll()`. Сейчас контроллеры ПЭК и протоколов дополнительно покрыты `@PreAuthorize`, однако безопасность новых маршрутов зависит от сохранения префикса `/api` или корректной method-аннотации.

Файл: `src/main/java/kz/eco/config/SecurityConfig.java:95-124`.

Рекомендация: использовать deny-by-default (`anyRequest().denyAll()`) и явно разрешить только статические ресурсы/SPA routes.

## Что проверено положительно

- Программа ПЭК: полный workflow `DRAFT → UNDER_REVIEW → RETURNED/APPROVED → ACTIVE → ARCHIVED`, readiness, версии/снимки, разрешения и контрольные мероприятия.
- Отчёт ПЭК: сбор источников, идемпотентность, plan/fact, превышения и корректирующие действия, readiness, официальный/внутренний документы, подпись актуальной версии, реквизиты официальной сдачи.
- Протоколы: типовые validation policies, контроль неизменяемости после утверждения/подписания, версии контента/PDF, аудит скачивания, привязка к ПЭК и company scope.
- Доступ: контроллеры трёх модулей имеют role gates; в коде присутствуют отдельные company/object access checks и тесты межфирменной изоляции.
- Конкурентность: используются `@Version`/If-Match и существуют тесты conflict/concurrency/idempotency.

## Проверка тестов

- Обнаружено более 100 тестовых классов по ПЭК и протоколам, включая E2E, company isolation, signing, idempotency, document generation и workflow guards.
- Полный прогон не состоялся: `mvnw.cmd test` падает внутри wrapper до запуска Maven; команда `mvn` в среде отсутствует; готовых `target/surefire-reports` в архиве нет.
- Поэтому заключение о прохождении тестов не выдаётся. После исправления wrapper обязательны `test`, `package` и отдельный smoke-тест с MySQL + MongoDB.

## Решение о готовности

Статус: **условно не готово к production** до устранения P0 с demo-аккаунтами и получения зелёного воспроизводимого тестового прогона. После этого P1 с хранением admin JWT следует закрыть до публичного запуска административной страницы; P2 допустимы только как явно принятый временный технический долг.
