# Проверка исправления выбора точек ПЭК — v23

Дата: 2026-09-16  
Архив: `eco-master (23).zip`  
Сравнение: `eco-master (22).zip`

## Итог

Backend-логика выбора конкретной точки или всех точек в целом реализована по контракту. Однако архив **нельзя безопасно разворачивать поверх базы, на которой уже применялась V128 из v22**: содержимое ранее существовавшей Flyway-миграции V128 изменено, её checksum отличается.

## Реализовано корректно

- `monitoringPointId` и `appliesToAllPoints=true` взаимоисключаются; код ошибки `PEK_CONTROL_ITEM_POINT_AMBIGUOUS`.
- Проверяются отсутствующая точка, чужая программа и другое направление; код `PEK_MONITORING_POINT_INVALID`.
- Ненастроенная позиция даёт одно требование `CONFIGURATION_REQUIRED`, а не размножается по всем точкам.
- Прямой `POST /api/protocols/from-pek` также запрещает создание по ненастроенной позиции.
- Конкретная точка не размножается по остальным точкам направления.
- `appliesToAllPoints=true` формирует требование для каждой точки направления.
- Удаление используемой точки блокируется кодом `PEK_MONITORING_POINT_IN_USE`.
- При клонировании программы направления и точки клонируются, а позиции перепривязываются к точкам новой программы.
- Старые неоднозначные строки больше не переводятся автоматически в режим «все точки».
- Добавлен ручной SQL-отчёт и шаблон безопасного исправления данных по явным ID.
- Добавлены профильные тесты перечисленных сценариев.

## Блокирующая проблема миграции

Файл `V128__pek_control_item_applies_to_all_points.sql` уже существовал в v22, но в v23 его содержимое изменено:

- SHA-256 v22: `0985E11F1A87E9ADC89DB48B2A0966EC1EF680691EA9428D65893B51063EB8AE`
- SHA-256 v23: `8B75377B9D0BB2A5802DADC7A9C0F903210667C0F4CB0493B09759A89083FE28`

Если старая V128 присутствует в `flyway_schema_history`, обычный запуск Flyway завершится ошибкой checksum validation. Нельзя просто заменять применённую versioned migration.

Нужен один из вариантов:

1. Если V128 нигде не применялась — v23 можно разворачивать с новой V128.
2. Если V128 уже применялась — вернуть исходный файл V128 без изменений и добавить новую миграцию V129, исправляющую данные/схему только вперёд. Для уже ошибочно выставленного `applies_to_all_points=true` автоматический откат неоднозначен; нужен отчёт и ручная корректировка по ID.

`flyway repair` допустим только после отдельного анализа состояния БД и не исправляет смысл уже изменённых строк.

## Проверка тестов

`mvnw.cmd -q -DskipTests compile` снова падает до запуска Maven:

```text
Cannot index into a null array.
Cannot start maven from wrapper
```

Java 21 в проверочной среде отсутствует, поэтому новый `PekControlItemPointSelectionTest` фактически не запускался. Наличие тестового класса не является подтверждением зелёного прогона.

## Что требуется перед deployment

1. Проверить `flyway_schema_history` production на версию 128.
2. Не выкладывать изменённую V128 поверх уже применённой V128.
3. Исправить Windows Maven Wrapper и выполнить полный тестовый прогон на Java 21.
4. Выполнить `PekControlItemPointSelectionTest` и полный `mvn test`.
5. На копии MySQL 8 production проверить V127/V128 либо корректную новую V129.
6. Выполнить `docs/pek-control-item-points-data-fix.sql`: сначала только отчёт, затем вручную назначить реальные ID северной и южной точек.
